## 1. Purpose — what shipped

PR #31 makes order side-effects durable and eventually delivered without `2PC`. Every `OrderService.placeOrder:121` / `confirm:143` / `status change:170,224,241` writes `OutboxEntry.pending("Order", id, eventType, payload JSON):125` in the **same** DB transaction as `Order+OrderItem+Payment`. A polling relay `OutboxPublisher.java:28` (`@ConditionalOnProperty app.kafka.enabled true:27`, `@Scheduled pollMillis 2000:56`, `batchSize 50:45`) claims `PENDING` rows with `FOR UPDATE SKIP LOCKED:24`, publishes via `OrderEventProducer/ObjectMapper` (`KafkaTemplate JsonSerializer:102`), marks `PUBLISHED:69` only after broker ack; failures `registerAttempt:72` stay `PENDING` for next poll → at-least-once. Consumer `OrderEventConsumer.java:33 @KafkaListener` `group order-service:104 ack MANUAL:114` processes `OrderPlacedMessage` and `CartCheckoutEventConsumer:53` for `cart.checkout.initiated`; poison after retries is routed by `KafkaConfig.kafkaErrorHandler:64 DefaultErrorHandler` to `order-events.DLT:37` (`TopicPartition DLT:67`) via `KafkaTemplate:64`. Topics configured as `NewTopic` beans `orderEventsDltTopic:36`.

## 2. Problem — before/after + Theory (first principles)

**Before:** `OrderService` committed order state but had no consumer-visible event: Kafka `KafkaConfig @EnableKafka:25` absent, `OutboxEntry.java:17` nonexistent, `OrderEventProducer:20 KafkaTemplate` never called. Dual write `DB.commit` + `kafkaTemplate.send` without atomicity risked **lost event** (DB commit, Kafka send failed, no recovery row) or **phantom event** (Kafka sent, DB rolled back, consumer sees ghost order). No `SKIP LOCKED`, no DLT: a single poison `JSON` would block `partition` forever.

**After:** Transactional outbox: `outbox.saveAndFlush(pending):125` inside `OrderService` tx guarantees exactly one `PENDING` row per business event. `OutboxPublisher.publishPendingNow:64 @Transactional` `lockPendingBatch(batchSize):66` does `SELECT ... FOR UPDATE SKIP LOCKED LIMIT :limit:24` — multiple `order-management-api` pods poll concurrently without double-delivery (locked rows skipped). `publishEntry:82` switches `eventType` `OrderPlacedEventMessage` → `orderPlacedProducer`, `OrderStatusChangedMessage` → `statusChangedProducer`, default legacy `OrderPlacedMessage` → `legacyProducer:94-100`. After `send`; `markPublished:69 + save:76 flush78`. Consumer `OrderEventConsumer 33 group order-service 104 earliest 105 manual ack 114` `receive + ack` idempotently; `KafkaConfig 64 errorHandler` after short retries publishes to `topic+".DLT":67` so poison never blocks group.

### Theory — Outbox, SKIP LOCKED, at-least-once, DLT from first principles (100+ lines)

#### 2.1 The dual-write problem — why outbox exists

```
[Client] → OrderService (@Transactional) → orders, order_items, payments COMMIT ?
                                                         ├─► Kafka send (2PC? no)
```

Kafka cannot join `DataSource` XA (`no distributed 2PC`). Two naive options both lose: (a) `DB commit then send` — send throws `TimeoutException`, DB already committed, consumer never sees event (lost); (b) `send then commit` — DB constraint violation rollbacks after Kafka already delivered (phantom). Outbox (`OutboxEntry.java:17 comment 17-18`) solves by **deferring external publish**: the tx writes `outbox status PENDING:10` row (`OutboxStatus:10 PENDING/PUBLISHED`) with the same `DataSource` connection; external relay (`OutboxPublisher`) later publishes. Exactly once per business row; relay may retry → at-least-once.

#### 2.2 Outbox row shape — `OutboxEntry.java` fields

`OutboxEntry:25` `id : autogenerated`, `aggregateType "Order":60`, `aggregateId orderId`, `eventType OrderPlacedEventMessage / OrderStatusChangedMessage`, `payload JSON String`, `status PENDING:45`, `attempts 0`, `createdAt`. `pending() factory:60` builds; `markPublished:71` sets `PUBLISHED`; `registerAttempt:72` bumps `attempts`. `OutboxRepository:10 JpaRepository<OutboxEntry,Long>` `countByStatus(PENDING):12` for health. `Jackson ObjectMapper:5` serialize before tx commit — payload frozen at tx time, not derived later.

#### 2.3 `FOR UPDATE SKIP LOCKED` — concurrent relay without coordination

`OutboxRepository:24 lockPendingBatch(@Param limit int limit)` native:

```sql
-- OutboxRepository.java:24
SELECT * FROM outbox WHERE status='PENDING' ORDER BY id LIMIT :limit FOR UPDATE SKIP LOCKED
```

`FOR UPDATE` locks rows for this tx (`publishPendingNow:64 @Transactional`). `SKIP LOCKED` makes concurrent pollers skip already-locked rows instead of blocking — essential for `replicas 2: k8s/deployment.yaml` both polling `2000ms:56`. Without `SKIP LOCKED`, pod B would block on `FOR UPDATE` until pod A commits — tail latency `2s`. With it, B gets next unlocked batch instantly. Alternative `FOR UPDATE NOWAIT` would throw on contention (worse). `lockPendingBatch` ordered by `id` gives FIFO publish order per aggregate (global order not guaranteed across partitions — `Kafka key = aggregateId` preserves per-order ordering via same partition).

```
Pod A tx1: lockPendingBatch 50 → ids 1..50 FOR UPDATE (locked)
Pod B tx2: lockPendingBatch 50 → ids 1..50 SKIP LOCKED → ids 51..100 (no wait)
```

#### 2.4 At-least-once and idempotency — consumer contract

`OutboxPublisher.publishPendingNow:64` marks `PUBLISHED:69` only after `orderPlacedProducer.publish:87` completes (broker ack `JsonSerializer:102`). If publish throws, `catch 71 registerAttempt72 log warn73` and `save76` keeps `PENDING` — next `scheduledPoll:56 2s` retries, doubling `attempts`. Broker-at-least-once implies consumer may see same `aggregateId` twice (publish succeeded but `save` before `flush78` crashed before commit). Consumer must be idempotent: `OrderEventConsumer:33` `ackMode MANual:114` processes then `acknowledgment.acknowledge()` explicitly; duplicate `OrderPlacedMessage` keyed by `aggregateId` checked via `IdempotencyService/IdempotencyRecord.java` or natural `order_number` unique constraint.

#### 2.6 Topic configuration and DLT — `KafkaConfig.java`

`KafkaConfig:27 @Configuration @EnableKafka:25` declares `NewTopic orderEventsDltTopic:36` for `order-events.DLT:197 partitions 3 replication 1` (defaults in `application-kafka.yml`). `kafkaErrorHandler:64 DefaultErrorHandler(KafkaTemplate, backoff)` with `DeadLetterPublishingRecoverer:67 (record, ex) -> new TopicPartition(record.topic()+".DLT", record.partition())`. After `maxRetries` (default `9` with `1s` backoff configured at `KafkaConfig:60-62`), poison `record` auto-published to `order-events.DLT`. Consumer `OrderEventConsumer 47 @KafkaListener topics order-events-dlt` logs `warn 51` for manual triage (replay via `kafka-console-consumer` or `KafkaTemplate` re-send).

```
Producer: order-events (key aggregateId) ─► Consumer group order-service 104 manual ack 114
                     poison after 9 retries ─► kafkaErrorHandler 64 → order-events.DLT 197 → DLT listener 47
```

Alternative `SeekToCurrentErrorHandler` without DLT would infinite retry blocking partition; `DLT` isolates poison so group progresses. Consumers `OrderPlacedEventConsumer 33` and `CartCheckoutEventConsumer 53` share template but distinct `topics cart.checkout.initiated 199`.

#### 2.7 Ordering, partitioning, and `aggregateId` key

`OrderPlacedEventProducer.publish(aggregateId, message:87)` uses `KafkaTemplate.send(topic, aggregateId, message)` — `aggregateId` string `String.valueOf(order.getId())` is the `key` (`StringSerializer:101`). Kafka partitioner hashes key → same `orderId` always same partition → ordered per order. Cross-order ordering not needed; `Outbox publisher` preserves `id` FIFO within batch but across batches order is still partition-key stable. Changing `key` to `null` would round-robin and lose order guarantees.

#### 2.8 Polling vs Change Data Capture — why polling here

Polling relay `OutboxPublisher:56 fixedDelay 2000ms` simple, no infra besides DB; latency `~2s` mean. Alternative Debezium CDC tails WAL (`pgoutput` slot) with `~10ms` latency and no polling query, but needs `Debezium connector` + `Kafka Connect` cluster. Tradeoff: polling queries `SELECT ... SKIP LOCKED` every `2s` even idle (`50` rows no-op), CDC is push-based. Learning journey chooses polling for zero operator burden; append `pg_stat_activity` check for idle skip.

#### 2.9 Payload evolution — `OrderPlacedEventMessage` vs legacy `OrderPlacedMessage`

`publishEntry:82 switch eventType` covers three branches: `OrderPlacedEventMessage:84` (current), `OrderStatusChangedMessage:89` (status), default `OrderPlacedMessage:96` legacy `order-events` topic `202`. `ObjectMapper.readValue(payload, Type:85,90,96)` deserializes stored JSON — schema evolution requires `Jackson` `@JsonIgnoreProperties(ignoreUnknown=true)` or versioned `eventType`. Legacy path kept for rollback compatibility; `topics legacy-order-events 202` still consumed by older deployments.

#### 2.10 Failure windows — where exactly once breaks

Exactly once per business action holds only if `OutboxEntry` row commit succeeds. Windows: `publishEntry` succeeds + `markPublished` save flushed but tx rollback due to `flush78` constraint violation → `PENDING` remains (retry safe duplicate after success — idempotent consumer required). Broker `acks all` with `retries` ensures produce not lost, but `JsonSerializer unsupported type` would poison before `DLT`. `app.outbox.scheduler-enabled false:206` disables relay for maintenance.

#### 2.11 Transaction boundary — `@Transactional` on publisher batch

`publishPendingNow:64 @Transactional` holds `FOR UPDATE` locks until method returns. Each `entry markPublished69 save76` stays in same persistence context; final `outbox.flush78` sends `UPDATE outbox SET status='PUBLISHED'` together. `Exception 71 per entry` not aborting whole batch is intentional: one poison `ObjectMapper` failure increments `attempts` while others publish.

#### 2.12 Backpressure — `batchSize 50` vs poll period

`batch 50:205` × `2s:204` = `25 msg/s` per pod steady; `2` pods `50 msg/s`. Bursty `100 orders` create `100 PENDING` rows visible as `countByStatus(PENDING):12` `50+50` over two polls `4s`. Smaller `batch 10` more DB round-trips; larger `500` holds locks longer. Tune `batch` with `Hikari 34 10` connection hold duration.


#### 2.13 Producer idempotence and `acks` trade

`spring.kafka.producer acks` default `1` (leader only) vs `all` (ISR). `KafkaTemplate` default `acks all` with `retries` ensures broker-committed before `markPublished69`; `acks 1` risk `leader crash` lost even though `markPublished` set `PUBLISHED`. Learning journey stays `acks 1` default but `Outbox` retry would re-deliver; switching to `acks all` + `enable.idempotence true` gives `exactly-once per producer session` (duplicate seq rejected).

#### 2.14 Tombstone and compaction alternative

`order-events` could be `compacted` (tombstone `null` value per `aggregateId` retain latest) vs `delete` policy `168h`. Choosing `delete` here because `Outbox` history queried via `EventStore`; compacted would dedupe old placements useful for `EventStoreService` replay.

## 6. Key decisions & tradeoffs

| Decision | Chosen | Alternative | Why | Cost |
|---|---|---|---|---|
| Transactional outbox `pending125` same tx | `OutboxEntry` row `PENDING` atomically with order | `send after commit` dual write | No lost/phantom events; crash recovers `PENDING` | `2s` poll latency; extra `outbox` table |
| `FOR UPDATE SKIP LOCKED:24 LIMIT batch50` | Skip locked `66` multi-pod | `FOR UPDATE` block / `advisory lock` | `2` pods poll concurrently non-blocking; FIFO per batch | Idle `2000ms` polls even empty |
| At-least-once `markPublished69` after ack | Publish then save vs save then publish | Exactly-once via 2PC/Kafka transactions | Broker ack before mark ensures no lost; duplicate possible → idempotent consumer | Duplicate delivery must be handled |
| `JsonSerializer:102` `ObjectMapper 85` | JSON payload stored | `Avro/SchemaRegistry` | No registry infra in learning journey; trusted `110` | Schema drift requires `ignoreUnknown` |
| `DefaultErrorHandler → DLT67` | `DeadLetterPublishingRecoverer` 3 retries `1s` | Infinite retry blocking partition | Poison never blocks group `order-service 104` | Triage via `DLT listener47 warn51` |
| `manual ack:114` consumer | Explicit `acknowledge()` after handle | auto-commit `106 true` | Offset not advanced on failure; `earliest 105` replay control | Must `acknowledge`; exception routes to DLT |
| Poll `2000ms 204 batch50 205` | `50/2s` | `CDC Debezium` push `10ms` | Zero infra, simple; `Testcontainers` friendly | `2s` mean latency; throughput `25/s` per pod |
| Legacy fallback `OrderPlacedMessage:96` | Switch default branch `94-100` | Single event type | Rollback compatibility `legacy-order-events202` | Extra branching |

## 9. Interview lens — Q&A

**Q1: Why outbox not just send after DB commit?**
A: Crashed between commit and send loses event (no row); sent then rolled back ghosts consumer. Same-tx `OutboxEntry PENDING45 pending60 125` makes relay recoverable (§2.1).

**Q2: How does `SKIP LOCKED:24` avoid double delivery with 2 pods?**
A: `FOR UPDATE` locks batch for tx `64`; concurrent poller skips locked rows instead of blocking, so `replicas 2` naturally shard without coordination (§2.3).

**Q3: At-least-once vs exactly once?**
A: Relay marks `PUBLISHED69` only after broker ack; crash before `save76 flush78` leaves `PENDING` retry → duplicate possible; consumer idempotent via `acknowledge manual114` + `IdempotencyRecord` (§2.4).

**Q4: What happens to a poison JSON that always deserializes fail?**
A: `DefaultErrorHandler:64` retries `3× 1s`, then `DeadLetterPublishingRecoverer67` publishes to `order-events.DLT197` (same partition); `DLT listener47 warn51` prevents group block (§2.6).

**Q5: How is per-order ordering preserved?**
A: `aggregateId String orderId:87` as `Kafka key StringSerializer101` hashes to same partition — FIFO per order; `Outbox` `ORDER BY id LIMIT 24` gives batch FIFO (§2.7).

**Q6: Polling vs CDC trade?**
A: Polling `2000ms204 batch50` simple no operator but `2s` latency; CDC `Debezium WAL` `~10ms` push but needs `Connect` cluster (§2.8).

**Q7: What verifies that the tx is truly atomic?**
A: `OrderServiceTest` places order, asserts `orders count 1` and `outbox PENDING 1` in same tx; `psql SELECT ... FROM outbox` before/after `publishPendingNow64`; `spring-kafka-test 208 EmbeddedKafka` drives deterministic relay.

## 10. Honest limits & next step → PR #32
